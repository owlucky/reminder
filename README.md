# Reminder Service — лёгкий сервис-напоминалка

Сервис хранит напоминания и **формулирует задачи доставки**. Отправляют их
отдельные процессы-воркеры: один или несколько Telegram-ботов, консоль,
позже — мессенджер Макс. Схема как в taxi: один формирователь и
распределитель, воркеры конкурируют за очередь и их можно поднимать
параллельно.

## Возможности

- **Разовые и периодические** напоминания: `once` / `daily` / `weekly` /
  `monthly` / `yearly` (годовые удобны для дней рождения) с интервалом
  (каждые N периодов).
- **Несколько напоминаний до события**: список смещений, например
  «за неделю», «за день» и «в момент» → `["1w", "1d", "0"]`.
- **Получатели — люди и группы**: у напоминания может быть несколько
  получателей; групповой чат Telegram тоже просто получатель с `chat_id` группы.
- **Воркеры каналов**: сервис не шлёт сообщения сам. Telegram-бот, консоль
  или будущий Макс — отдельные процессы, которые забирают задачи своего канала.
- **Полное отключение** (`disable`/`enable`) и **временная пауза**
  (`snooze`, по умолчанию на месяц).
- **Надёжность**: задача на каждого получателя, дедупликация, аренда с возвратом
  в очередь, если воркер умер, досыл пропущенного после простоя сервиса
  в пределах grace-окна.
- **Легковесность**: SQLite + FastAPI + APScheduler. Базу открывает только сервис.

## Архитектура

```
сервис (один процесс)                воркеры (сколько угодно процессов)
  API + SQLite                         telegram   telegram-2   console   max
  formulator  — какие доставки пора         \        |         /        /
  distributor — кому отдать задачу      POST /internal/tasks/next
                                        POST /internal/tasks/{id}/result

app/
  main.py          — FastAPI и планировщик, без бота и без отправки
  formulator.py    — из наступивших напоминаний делает строки очереди
  distributor.py   — аренда задачи воркером и приём результата
  scheduler.py     — фоновый опрос (APScheduler)
  models.py        — Reminder, Recipient, DeliveryTask
workers/
  loop.py          — общий цикл: взять задачу, доставить, сдать результат
  telegram.py      — один Telegram-бот (чат + доставка)
  console.py       — печать в лог
  max.py           — заготовка, очередь канала max не разбирает
```

## Быстрый старт (Docker)

```bash
cp .env.example .env
# впишите TELEGRAM_BOT_TOKEN (получить у @BotFather)
# если порт 8000 смотрит наружу — задайте INTERNAL_TOKEN и там, и у воркеров

docker compose up --build
```

Сервис — http://localhost:8000, документация — http://localhost:8000/docs.
Рядом поднимается один `telegram-worker`. Данные SQLite — в томе `./data`,
его монтирует только сервис.

Второй бот (другой токен, свои чаты):

```bash
# в .env: TELEGRAM_BOT_TOKEN_2=...
docker compose --profile bot2 up --build
```

Без Telegram, только печать задач в лог:

```bash
docker compose --profile console up --build
```

## Быстрый старт (локально)

```bash
python -m venv .venv
. .venv/Scripts/activate        # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Во втором терминале — воркер. Консоль:

```bash
python -m workers.console
```

Telegram (в `.env` должны быть `TELEGRAM_BOT_TOKEN` и `SERVICE_URL`):

```bash
python -m workers.telegram
```

Каждый дополнительный бот — ещё один процесс со своим токеном
(`TELEGRAM_BOT_TOKEN` / `WORKER_ID` в окружении именно этого процесса).

## Как это работает

1. Заводите **получателей** (`/recipients`) — кому и через какой канал слать.
2. Создаёте **напоминания** (`/reminders`) — что, когда, с какой периодичностью,
   за сколько до события и каким получателям.
3. Планировщик каждые `POLL_INTERVAL_SECONDS` секунд **формулирует** задачи:
   для каждого получателя, у которого наступил `момент_события - смещение`,
   в очередь попадает одна строка. Ключ дедупликации не даст поставить её дважды.
4. Воркер своего канала опрашивает `POST /internal/tasks/next`, арендует задачу
   и после отправки сдаёт результат. Упал, не сдав результат — по истечении
   аренды задача снова доступна другому воркеру того же канала.
   Неудача повторяется с паузой, пока не исчерпан `MAX_DELIVERY_ATTEMPTS`.
5. У получателя может быть `route_key`. Telegram-воркер ставит
   `telegram:<id бота>` (из `getMe`). Чужой бот такую задачу не возьмёт.
   Пустой `route_key` заберёт любой воркер этого канала — удобно, когда бот один.

## Примеры API

Получить `chat_id`: напишите своему боту, затем откройте
`https://api.telegram.org/bot<TOKEN>/getUpdates` — там будет `chat.id`.

### Получатель (Telegram)

```bash
curl -X POST http://localhost:8000/recipients \
  -H "Content-Type: application/json" \
  -d '{"name": "Иван", "channel": "telegram", "address": "123456789"}'
```

### Напоминание о дне рождения (ежегодно, за неделю и в день)

```bash
curl -X POST http://localhost:8000/reminders \
  -H "Content-Type: application/json" \
  -d '{
        "title": "День рождения Ивана",
        "event_time": "1990-05-05T09:00:00Z",
        "recurrence": "yearly",
        "offsets": ["1w", "0"],
        "recipient_ids": [1]
      }'
```

### Напоминание о дедлайне (разово, за день и за час)

```bash
curl -X POST http://localhost:8000/reminders \
  -H "Content-Type: application/json" \
  -d '{
        "title": "Дедлайн: отчёт",
        "description": "Сдать квартальный отчёт",
        "event_time": "2026-07-15T18:00:00Z",
        "recurrence": "once",
        "offsets": ["1d", "1h"],
        "recipient_ids": [1]
      }'
```

### Управление

```bash
# временно отключить (по умолчанию на месяц)
curl -X POST http://localhost:8000/reminders/1/snooze
curl -X POST http://localhost:8000/reminders/1/snooze -H "Content-Type: application/json" -d '{"days": 14}'

# снять паузу / полностью выключить / включить
curl -X POST http://localhost:8000/reminders/1/unsnooze
curl -X POST http://localhost:8000/reminders/1/disable
curl -X POST http://localhost:8000/reminders/1/enable

# тестовая отправка сейчас, ближайшие срабатывания, список каналов
curl -X POST http://localhost:8000/reminders/1/test
curl http://localhost:8000/reminders/1/upcoming
curl http://localhost:8000/channels
```

## Telegram-бот (управление из чата)

Бот — отдельный процесс `python -m workers.telegram` (или сервис
`telegram-worker` в Compose). Long polling и разбор очереди живут в нём,
напоминания он создаёт через REST сервиса. `chat_id` определяется автоматически,
получатель привязан к этому боту через `route_key`.
**Все выборы делаются inline-кнопками.**

При первом обращении (`/start` или `/add`) бот просит выбрать **часовой
пояс** — кнопками. После этого дату/время вы вводите **в своём поясе**, и
все напоминания и даты в сообщениях показываются тоже в нём (проблема
рассинхрона с UTC решена). Сменить пояс позже — `/timezone`.

Команды:

| Команда | Действие |
| --- | --- |
| `/start` | приветствие + выбор часового пояса при первом запуске |
| `/add` | пошагово создать напоминание (заголовок и дата — текстом; повтор и смещения — кнопками) |
| `/list` | напоминания этого чата, с кнопками управления под каждым |
| `/timezone` | выбрать/изменить часовой пояс (кнопками) |
| `/cancel` | отменить текущий пошаговый ввод |
| `/help` | справка |

Команды бота зарегистрированы через `setMyCommands`, поэтому доступны по
кнопке **Menu** слева от поля ввода — листать историю вверх не нужно.

Управление конкретным напоминанием — кнопками под ним в `/list`:
**📨 Тест**, **✏️ Изменить**, **⏸ Пауза**, **🚫 Выключить / ✅ Включить**,
**🗑 Удалить** (с подтверждением). Кнопка **✏️ Изменить** позволяет поменять
«когда напоминать», повтор, дату/время и заголовок — тоже кнопками.

**⏸ Пауза** открывает выбор срока (1 час / 1 день / 3 дня / 1 неделя /
2 недели / 1 месяц) или свой вариант текстом (например `2d`, `1w`, `12h`).

Напоминания нумеруются **внутри чата** (№1, №2, …), независимо от внутренних
id в базе.

**Разовое напоминание нельзя поставить в прошлое** — при вводе прошедшей даты
бот попросит ввести будущую. Для повторяющихся дата события может быть в
прошлом (например, дата рождения для ежегодного напоминания) — оно всё равно
сработает в ближайшую годовщину.

В `/add` бот сам создаёт получателя для чата. В групповом чате получателем
становится сама группа — напоминание получат все участники.

Только REST, без бота: не запускайте `workers.telegram`. Сервис от этого не зависит.

## Смещения (offsets)

Строка `<число><единица>` или число секунд. Единицы: `s`, `m`, `h`, `d`, `w`.
Примеры: `"0"` (в момент события), `"30m"`, `"2h"`, `"1d"`, `"1w"`.
Каждое смещение — отдельное напоминание до события.

## Добавить канал (например, Макс)

1. Добавьте имя в `KNOWN_CHANNELS` (`app/channels.py`), если его ещё нет.
   `max` уже там: получателя можно создать, задачи будут ждать воркера.
2. Новый процесс по образцу `workers/console.py` / `workers/telegram.py`:
   цикл `PullLoop` с `channel="max"`, свой `deliver()`, при необходимости
   свой приём апдейтов. `workers/max.py` пока только объясняет это и выходит,
   очередь он не трогает.
3. Поднимите сколько угодно таких процессов. Один сервис раздаёт задачи всем.

`POST /reminders/{id}/test` не шлёт сообщение сам: он ставит внеочередные
задачи, их забирает воркер канала.

## Настройки (.env)

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `TELEGRAM_BOT_TOKEN` | Токен бота для процесса `workers.telegram` | — |
| `TELEGRAM_BOT_TOKEN_2` | Токен второго бота (`--profile bot2`) | — |
| `SERVICE_URL` | Адрес сервиса с точки зрения воркера | `http://127.0.0.1:8000` |
| `INTERNAL_TOKEN` | Секрет заголовка `X-Internal-Token` | — |
| `DATABASE_URL` | Строка подключения к БД (только сервис) | `sqlite:///./data/reminders.db` |
| `POLL_INTERVAL_SECONDS` | Как часто формулируются задачи | `30` |
| `WORKER_POLL_SECONDS` | Пауза воркера, когда очередь пуста | `1` |
| `TASK_LEASE_SECONDS` | Аренда задачи | `60` |
| `MAX_DELIVERY_ATTEMPTS` | Попытки доставки до статуса `failed` | `5` |
| `MISSED_GRACE_SECONDS` | Досыл пропущенного после простоя сервиса | `21600` (6 ч) |
| `DEFAULT_SNOOZE_DAYS` | Пауза по умолчанию для snooze | `30` |
| `LOG_LEVEL` | Уровень логирования | `INFO` |

Живые воркеры (кто брал задачи последние 90 секунд) — `GET /workers`.
